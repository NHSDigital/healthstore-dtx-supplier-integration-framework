# Supplier Conformance Assessment List: Registrations API v1.0

This is the list of tests a DTx supplier runs, and records evidence for, before HealthStore accepts their product onto the Registrations API. Two calls are HealthStore's, both from the supplier's own app during the patient's NHS Login sign-in in that app. This is not the NHS Login the patient used earlier in the NHS App.

1. `GET /registrations`, after the supplier's own NHS Login `/userinfo` call.
2. `POST /registrations/{registration-id}/tasks`, one Task per open registration, registered or rejected with a coded reason, in the same sign-in.

The same checks can be run from the Registrations Postman collection: [ LINK / COLLECTION / SCRIPT TO BE CONFIRMED ]

That POST path is the only acknowledgement endpoint in v1.0. Each outcome below is a body on that path. Activation, deactivation, off-boarding, and retraction are a later version of the same path. See [`lifecycle.md`](https://github.com/NHSDigital/healthstore-dtx-supplier-integration-framework/blob/main/docs/registration-api/lifecycle.md).

The supplier fills the evidence column with a captured request and response, or a test log, from their own system. HealthStore QA reviews the completed list. A completed copy for a named supplier is not stored in this repository.

The contract tests in [`tests/contract-validation/healthstore-api.test.js`](../../tests/contract-validation/healthstore-api.test.js) call a mock of [`specification/healthstore-api.yaml`](../../specification/healthstore-api.yaml). They show the shape the spec accepts. They do not call HealthStore. A row marked "HealthStore" is behaviour the schema cannot express. That row waits until the service implements it.

## Non-functional rows

NFR-P11-F, NFR-P11-H, NFR-P11-I and NFR-P03-S are copied from the programme [Non-Functional Requirements](https://nhsd-confluence.digital.nhs.uk/spaces/DTX/pages/1395204611/Non-Functional+Requirements) page, Load and Performance NFRs. That page says targets are p95 unless stated otherwise. NFR-P11-F, NFR-P11-H and NFR-P11-I are Private Beta. NFR-P03-S is phase TBD.

The rate-limit rows still have no signed limit. Do not invent one.

On API Management, rate limiting is the `x-nhsd-apim` extension `ratelimiting`. It has two limits, and each needs its own NFR:

- `app-default` limits one consuming application. That is the per-supplier limit.
- `proxy` limits the whole Registrations API, all suppliers combined.

The numbers in an example of that extension, such as 5 per minute on the proxy and 10 per minute per application, are not the Registrations limits. A figure of 100 requests per second has been described as reasonable for a national service. It is not signed for this API. The signed values are copied here when they exist.

When a limit is exceeded, the call returns `429` `TOO_MANY_REQUESTS` with `Retry-After`. The contract test `429 carries Retry-After` covers that shape on `GET /registrations`. How APIM turns `limit` into an Apigee quota and spike arrest is still open. A spiky load test is the check, once the numbers are signed.

## Recoverability

These tests show the supplier recovers from the failures in the [error table](https://github.com/NHSDigital/healthstore-dtx-supplier-integration-framework/blob/main/docs/registration-api/resources.md#errors). A retry repeats the same `X-Request-ID`. A terminal error is not sent again unchanged: the supplier follows the class in that table, then makes a later call that succeeds.
